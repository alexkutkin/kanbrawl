# Kanbrawl MCP — список задач

**Контекст.** MCP — основной интерфейс продукта: агенты читают, создают, двигают и правят задачи. Веб-UI и REST — вторичные поверхности. Этот файл уточняет и заменяет MCP-часть из `kanbrawl-ux-ui-tasks.md`: KB-MCP-04 заменяет KB-UX-04, KB-MCP-10 расширяет KB-UX-11.

**Легенда.** P0 — доверие и контракт, P1 — важное, P2 — полировка, P3 — позже. S/M/L — примерный размер.

**Проверено на живых процессах** (временная доска, без изменений рабочей):
- задача, созданная через stdio, не видна HTTP-серверу (`/api/board` = `[]`); следующая запись через HTTP удалила её с диска;
- `kanbrawl start --stdio` открывает HTTP API на порту: `GET /api/board` → 200, в лог печатаются LAN-адреса;
- `POST /mcp` с `Origin: http://evil.example` → 200;
- после `PUT /api/columns` (Todo → Backlog) `list_tasks` без аргументов падает, а `create_task` работает; `tools/list` продолжает отдавать старые имена;
- `POST /api/tasks` с `priority: "P9"` → 200; после этого MCP `list_tasks` падает с `-32602 Output validation error`;
- `PATCH /api/tasks/:id` с `title: "   "` → 200, в файле пробелы;
- 20 параллельных MCP-вызовов в одном HTTP-процессе → 20/20 успешно.

## Этап 1 — контракт и целостность

### [x] KB-MCP-01 — Один источник истины для stdio, HTTP и CLI (P0, L)

**Проблема.** Каждый процесс создаёт свой `BoardStore`: HTTP — `src/server/index.ts:91`, stdio — тот же `startServer`, CLI — `src/cli/commands/task.ts:13`. `kanbrawl init` пишет stdio-конфиг каждому инструменту (`src/cli/commands/init.ts:15`), поэтому два AI-клиента и открытый веб-UI — это три писателя одного файла. Проверено: задача из stdio не видна HTTP, а следующая HTTP-запись стёрла её с диска.

**Что сделать.**
- Выбрать одного владельца состояния. Предпочтительно: stdio-сервер — тонкий клиент к запущенному HTTP-серверу (подключиться, а если его нет — поднять и подключиться).
- Альтернатива, если оставляем файл: перечитывать файл перед каждой мутацией, писать temp + rename, не держать состояние в памяти без проверки mtime.
- Не смешивать: либо файл — единственный источник с блокировкой, либо HTTP-процесс — единственный писатель.

**Готово, когда.** Задача, созданная через stdio, видна в UI без reload; два stdio-клиента и HTTP не теряют задачи; есть тест на два процесса с временной доской.

**Файлы.** `src/server/index.ts`, `src/server/store.ts`, `src/cli/commands/init.ts`, `src/cli/commands/start.ts`.

**Источник.** MCP transports: stdio — один клиент на процесс, HTTP — общий сервер; prior art: серверы с БД имеют одного писателя.

### [x] KB-MCP-02 — `--stdio` не должен поднимать HTTP/SSE (P0, S)

**Проблема.** `app.listen` вызывается вне условия `options.stdio` (`src/server/index.ts:157`). Проверено: `PORT=18433 kanbrawl start --stdio` → `GET /api/board` 200 и печать LAN-адресов. Каждый инструмент, запустивший stdio-сервер, открывает неаутентифицированный REST/SSE.

**Что сделать.** В stdio-режиме не создавать Express и не слушать порт. Если SSE нужен внутри stdio — только loopback и токен.

**Готово, когда.** `kanbrawl start --stdio` не открывает TCP-порт; MCP-инструменты работают; в stderr нет LAN-адресов.

**Файлы.** `src/server/index.ts`.

**Источник.** MCP transports: stdio не предполагает сетевого сервера.

### [x] KB-MCP-03 — Origin и доступ к LAN (P0, M)

**Проблема.** Нет проверки `Origin`; `app.listen(port)` слушает все интерфейсы; проверено: `POST /mcp` с чужим Origin → 200. Спецификация: «Servers **MUST** validate the `Origin` header… to prevent DNS rebinding attacks», локальные серверы должны слушать localhost и использовать аутентификацию. LAN-доступ — намеренная фича (коммит `b004bbb`), поэтому не удалять, а ограничить.

**Что сделать.**
- Allowlist Origin для `/mcp` (localhost + явно настроенные).
- По умолчанию слушать `127.0.0.1`; LAN — явный флаг `--host`/env.
- Для не-local запросов — токен (query/header) и понятная ошибка 401.
- Задокументировать в README/AGENTS.

**Готово, когда.** Чужой Origin получает отказ; по умолчанию порт недоступен из сети; LAN включается осознанно и защищён токеном.

**Файлы.** `src/server/index.ts`, `src/cli/cli.ts`, `README.md`.

**Источник.** MCP Streamable HTTP transport (Origin, localhost, auth).

### [x] KB-MCP-04 — `get_task`, выборка по всей доске, признаки усечения (P0, M)

**Проблема.** Нет `get_task`: зная id, агент не может получить задачу. `list_tasks` по умолчанию смотрит первую колонку (`src/server/tools.ts:112`) и молча режет до 10 (`:142`); при 12 задачах агент видит 10 и не знает об этом — это закреплено тестом. `hasMore`/`total` нет.

**Что сделать.**
- Добавить `get_task(id)`.
- `list_tasks` без `column` — все колонки; сохранить фильтры и `max` (<=1000).
- Вернуть `{ tasks, total, hasMore }` (и `offset`, если нужна постраничность).
- Тесты: поиск по id, 12 задач без потери информации, все колонки одним вызовом.

**Готово, когда.** Задача находится по id одним вызовом; ни одна задача не скрывается без явного признака.

**Файлы.** `src/server/tools.ts`, `src/server/tools.test.ts`.

**Источник.** Agent-first сценарий; KB-UX-04.

### [x] KB-MCP-05 — Колонки читать в момент вызова, не вшивать в схему (P0, S)

**Проблема.** `columnNames` снимаются один раз при регистрации (`src/server/tools.ts:19`) и попадают в описания (`:81`, `:178`, `:236`) и default (`:112`). Проверено: после rename Todo → Backlog `list_tasks {}` падает, `create_task` работает (store берёт живую первую колонку), а `tools/list` продолжает отдавать «Available: Todo…».

**Что сделать.**
- Убрать конкретные имена и default из статических описаний.
- Default резолвить в момент вызова (как уже делает `createTask`).
- В описании: «call `get_columns` first»; в AGENTS.md — тот же порядок.
- Тест: rename через `PUT /api/columns`, затем `list_tasks {}` и `tools/list` без старых имён.

**Готово, когда.** Схема инструментов не содержит состояния доски; rename не ломает вызовы.

**Файлы.** `src/server/tools.ts`, `src/server/tools.test.ts`, `src/cli/commands/init.ts`.

**Источник.** MCP: `tools/list` описывает возможности, а не текущее состояние; спецификация — статические схемы.

### [x] KB-MCP-06 — Валидация в `BoardStore`, а не только в Zod (P0, M)

**Проблема.** Ограничения живут только в MCP-схемах. REST принимает `priority: "P9"` и `title: "   "` (проверено). После P9 MCP `list_tasks` падает: `MCP error -32602: Output validation error: Invalid structured content`. Спецификация: сервер **MUST** отдавать `structuredContent` по `outputSchema` и **MUST** валидировать входы. Один плохой REST-запись ломает агентский инструмент.

**Что сделать.**
- Перенести правила в `BoardStore`: trim + непустой title <=200, description <=4000, assignee <=100, priority только P0/P1/P2.
- REST возвращает 400 с тем же текстом; UI получает понятную ошибку.
- При загрузке санитизировать старые данные (неизвестный приоритет → P1) или явно сообщать.
- Тесты через REST и MCP.

**Готово, когда.** Ни один путь записи не создаёт задачу вне контракта; доска с «плохим» приоритетом не ломает `list_tasks`.

**Файлы.** `src/server/store.ts`, `src/server/api.ts`, `src/server/tools.ts`, `src/server/*.test.ts`.

**Источник.** MCP tools: output schema, structured content, input validation.

## Этап 2 — удобство агента

### [x] KB-MCP-07 — `update_task` умеет `column` (P1, S)

**Проблема.** REST `PATCH /api/tasks/:id` меняет поля и колонку; MCP `update_task` колонку не умеет. Агент делает два вызова, между ними возможно частичное состояние, и у агента меньше возможностей, чем у REST.

**Что сделать.** Добавить optional `column` в `update_task`; в store обновлять поля и колонку одной операцией; события — по факту изменения.

**Готово, когда.** Один вызов меняет поля и колонку; невалидная колонка не оставляет частичных изменений.

**Файлы.** `src/server/tools.ts`, `src/server/store.ts`, `src/server/tools.test.ts`.

**Источник.** Agent-first: MCP не должен быть беднее REST.

### [x] KB-MCP-08 — Честные annotations и текст описаний (P1, S)

**Проблема.** `idempotentHint: true` у `move_task` (`src/server/tools.ts:242`) и `update_task` (`:297`), хотя они меняют `updatedAt` и шлют события — по спецификации «no additional effect on its environment» это неверно. У `delete_task` (`:342`) hint спорный: повторный вызов даёт ошибку. В описании опечатка «errorneous» (`:332`).

**Что сделать.** Поставить `idempotentHint: false` для move/update/delete; исправить опечатку; добавить snapshot-тест `tools/list`, чтобы annotations и описания не расходились с поведением.

**Готово, когда.** Annotations соответствуют поведению; тест фиксирует контракт.

**Файлы.** `src/server/tools.ts`, `src/server/tools.test.ts`.

**Источник.** MCP ToolAnnotations.

### [x] KB-MCP-09 — Машиночитаемые ошибки (P1, S)

**Проблема.** Ошибки — только текст: агенту нужно парсить «Column "X" does not exist». Успешные ответы структурированы, ошибки — нет.

**Что сделать.** Добавить стабильные коды: `COLUMN_NOT_FOUND`, `TASK_NOT_FOUND`, `INVALID_PRIORITY`, `CONFLICT`, `INVALID_ARGUMENT`. Сохранить человеческий текст и список доступных колонок. Формат — префикс в text или structured error, если SDK позволяет с outputSchema.

**Готово, когда.** Агент различает причины без парсинга прозы; тексты не потеряли полезные детали.

**Файлы.** `src/server/tools.ts`, `src/server/tools.test.ts`.

**Источник.** MCP: tool execution errors через `isError`; prior art — коды ошибок API.

## Этап 3 — полировка

### [x] KB-MCP-10 — Оптимистичная конкурентность (P2, M)

**Проблема.** В одном процессе store один (20 параллельных вызовов прошли), но между агентами действует last-write-wins: второй `update_task` молча перетирает поля первого. После KB-MCP-01 исчезнет потеря файла, но не потеря поля.

**Что сделать.** Optional `expectedUpdatedAt` (или `version`) в update/move; при расхождении — ошибка `CONFLICT` и актуальная задача в ответе. Без параметра поведение прежнее.

**Готово, когда.** Устаревшее обновление отклоняется с понятной ошибкой; старые вызовы работают.

**Файлы.** `src/server/tools.ts`, `src/server/store.ts`, `src/server/tools.test.ts`.

**Источник.** Agent-first concurrency; KB-UX-11.

### [x] KB-MCP-11 — Атомарная запись файла (P2, S)

**Проблема.** `writeFileSync` пишет прямо в `kanbrawl.json` (`src/server/store.ts:74`): обрыв или параллельная запись могут оставить битый JSON.

**Что сделать.** Писать во временный файл и переименовывать; при файловом режиме — перечитывать при изменении mtime (входит в KB-MCP-01).

**Готово, когда.** Прерванная запись оставляет предыдущую валидную доску; есть тест на temp+rename.

**Файлы.** `src/server/store.ts`.

**Источник.** Data integrity (inferred).

### [x] KB-MCP-12 — Идемпотентность ретраев `create_task` (P3, S)

**Проблема.** При таймауте и повторе агент создаёт дубль: `create_task` не идемпотентен.

**Что сделать.** Optional `clientRequestId`: повтор с тем же ключом возвращает ту же задачу. Если не нужно — явно написать в описании, что повтор создаёт дубль.

**Готово, когда.** Повтор с тем же ключом даёт одну задачу и тот же id.

**Файлы.** `src/server/tools.ts`, `src/server/store.ts`.

**Источник.** Idempotency keys (prior art, inferred).

## Не делать сейчас

- Resources, subscriptions и push-нотификации: агент работает циклом, HTTP-транспорт stateless.
- Cursor-пагинация: достаточно `offset`/`hasMore`.
- Batch-инструменты: два вызова дешевле обработки частичных ошибок.
- Мультидоска, мультиюзер, полноценная auth-система: локальный токен достаточен.
- Версионирование инструментов.

## Порядок работы

1. KB-MCP-01 + KB-MCP-02 — один писатель, никакого фантомного HTTP.
2. KB-MCP-03 — решить с пользователем режим доступа (localhost по умолчанию, LAN по флагу).
3. KB-MCP-04 + KB-MCP-05 + KB-MCP-06 — контракт агента.
4. KB-MCP-07 + KB-MCP-08 + KB-MCP-09 — эргономика.
5. KB-MCP-10…12 — по ёмкости.

## Проверки

- Для серверных изменений — тесты в `src/server/*.test.ts`; перед завершением `npm run build`, `npm run lint`, `npm test`.
- Регрессии из разбора: два процесса на временной доске (stdio + HTTP), rename колонки, запись `priority: "P9"` через REST, пустой title, `tools/list` после rename.
